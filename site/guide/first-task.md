# 跑通第一份小任务

第一单的目的很简单：**把一个明确要求，变成你实际收到、打开并核对过的成果。** 先用合成材料，不拿现有团队和私人业务试安装。

## 开工前确认三件事

1. 已按[平台指南](/guide/start)采用主 Skill，并核对实际使用的版本。
2. 已提供 `TASK-MATERIALS.zip` 或其解压目录；助手确实读到了本单需要的基础规则和配置。
3. 已有适合本单的制作成员、独立审核成员和收件入口。没有真实独立审核者，就如实记录缺口，不用同一个助手扮演几个名字代替。

## 用包里的会议纪要例子

任务资料里的 `foundation/examples/walkthrough-meeting-notes/input.md` 是合成输入，可用它走一遍流程。示例答案只用于后续对照，不预先当成制作结果。

| 阶段 | 具体动作 | 你应该看到什么 |
| --- | --- | --- |
| 定任务 | 明确纪要要保留的事实、交付形式、负责人和收件位置 | 一份具体任务，不是一句“帮我处理” |
| 制作 | 真实制作成员读取输入，交出纪要文件 | 可打开的初稿和版本标识 |
| 审核 | 另一个真实执行上下文打开**同一版**初稿，对照输入核遗漏与错误 | 有依据的问题或通过结论；首席不改写审核意见 |
| 修改 | 有问题交回原制作成员，按问题局部修订 | 修订稿及对应修改说明 |
| 交回 | 把成果和审核记录交到原收件入口 | 实际文件或可访问附件；你能打开并按要求验收 |

简单任务不用硬凑全部岗位，也不用填满所有表。需要多成员协作时，分别确认各自实际取得的材料和权限。

## 三件事不能混为一谈

- **说“已完成”**，不等于成果已经收到。
- **给出文件路径**，不等于原对话里有可下载附件。
- **审核通过**，不等于自动取得新的发布、付款或最终验收权限。

如果任务中断，用接续工具留下当前版本、未完成项、证据位置和下一步。新接手者实际读到这些内容后才能继续；工具不会自动唤醒助手。
